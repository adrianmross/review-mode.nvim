OVERVIEW                                                  *review-mode-overview*

review-mode.nvim keeps GitHub pull request review in ordinary file buffers. It compares the
current branch to the PR base, sets Gitsigns to that base when available, loads
review comments asynchronously, and provides commands for jumping through PR
hunks, PR comments, and changed files.

The plugin uses `gh` for PR metadata, comments, replies, thread state, checks,
and browser handoff metadata. The default comment sign is a Nerd Font glyph;
set `comments.sign_text` to a plain character if your font does not have it.
Picker integrations for snacks.nvim and Telescope are optional and fall back
to vim.ui.select.

==============================================================================
THE MODE                                                      *review-mode-mode*

The mode and the review session are separate. The session holds the PR context
(base ref, changed files, comments, viewed state); the mode is the key layer
and decorations over it.

Stepping out with |:ReviewModeLeave| restores your own mappings and puts the
Gitsigns gutter back to the index, so you can stage and commit normally, while
comment signs and nvim-tree markers stay visible and nothing is re-fetched.
Stepping back in with |:ReviewModeEnter| is instant. |:ReviewModeStop| is what
ends the session.

Keys installed while in the mode (see mode.keys to change them):

        ]c / [c         next / previous PR hunk (in a diff window, Vim's own
                        change jump)
        ]r / [r         next / previous PR comment thread
        ]f / [f         next / previous changed file

<leader>rm (or |:ReviewModeEnter| / |:ReviewModeLeave|) steps in and out.

A mapping shadowed by the layer is saved on entry and restored on exit.

Session keys are installed by :ReviewMode and removed by :ReviewModeStop. They
stay while you step out of the mode, since <leader> keys shadow nothing in stock
Vim (see session.keys to change them):

        <leader>rt      toggle the thread panel |review-mode-panel|
        <leader>rr      comment: reply to the thread on this line, or start
                        one where there is none; a visual range always
                        starts one, and several threads on a line ask which
        <leader>rR      start a new thread, even over an existing one
        <leader>rx      resolve / unresolve the thread on this line
        <leader>rf      changed files with viewed state and comment counts
        <leader>rv      toggle this file viewed
        <leader>rd      base diff (rD layout; zR / zM show / fold unchanged lines)
        <leader>ra      actions picker (every action, with its key)
        <leader>rs      pending review and submit
        <leader>rq      end the review

mode.keys and session.keys merge over the defaults; false removes one key and
{} installs none.

A commit made during the review joins it: the reflog is watched, and on the
next FocusGained, BufEnter or TermLeave the changed files and hunks are rebuilt
and the PR head SHA is re-fetched so new comments anchor to a commit GitHub
knows. Viewed state and loaded comments are kept. Set follow_head = false to
require |:ReviewModeRefresh| instead.

On a branch with no PR, :ReviewMode reviews it locally instead (see
|:ReviewModeLocal|) and says so; the statusline shows "local repo@ref". It falls
back only when gh answers that there is no PR, never on an auth, network or
rate-limit failure, and never for a PR named with GH_REVIEW_PR. Set
no_pr = "error" to report the missing PR instead.

With mode.workspace = "tab" the review keeps its own tabpage: entering focuses
it, leaving returns to the previous tabpage, and the layout survives in
between. Ending the session closes it. The default "inplace" leaves your
windows alone.

                                                        *review-mode-statusline*
vim.g.review_mode is "mode", "session", or nil.
require("review_mode").statusline() returns a short summary such as
"REVIEW owner/repo#123 3/12".

Review is a key layer over normal mode, not a real Vim mode, so mode() never
returns it and a statusline's stock mode component cannot show it.
require("review_mode").mode_text() stands in for that component: "REVIEW" while
the layer is live and you are in normal mode, "REVIEW INSERT" once you step
into another mode, and the plain mode name with no review, so normal/insert
context stays visible. It takes { label = "PR", separator = "." }.

With lualine: sections = { lualine_a = { { require("review_mode").mode_text } } }

The plugin fires these |User| autocommands: ReviewModeStart, ReviewModeEnter,
ReviewModeLeave, ReviewModeStop.

THREAD PANEL                                                 *review-mode-panel*

|:ReviewModePanel| opens a vertical split beside the file. It follows the
cursor: threads anchored to the current line, or every thread in the file when
the cursor is not on one. A thread shows its author, their association with the
repository, how long ago it was written, the reply chain, emoji reactions, and
whether it is open, resolved, or outdated. Fenced code inside a comment is
drawn as code instead of as more prose, and a `suggestion` block is drawn as
the diff it would apply: the lines it replaces above the lines it proposes.

Keys inside the panel:

        r       reply to the thread under the cursor (a new thread when
                the panel is empty)
        R       start a new thread on the line the code window is on
        x       resolve or unresolve the thread
        a       apply the thread's suggestion to the buffer
        o       open the comment on GitHub
        <CR>    jump to the thread's line in the code window
        ]r [r   next / previous thread in the panel
        <C-l>   reload comments from GitHub
        +       react to the comment under the cursor
        e       edit your comment under the cursor in a draft buffer
        dd      delete your comment under the cursor, after a confirmation
        s       open the pending review buffer |review-mode-pending|
        q       close the panel
        p       preview the suggestion in the code |review-mode-suggestions|
        A       apply every suggestion in the file, after a confirmation

Resolved threads are hidden in the panel and in |:ReviewModeThread| unless a
line has nothing else on it. Set comments.show_resolved = true to always show
them.

Resolving or unresolving a thread briefly marks the line it sat on, in the
colour of its new state, so the change is confirmed where you made it instead
of the comment merely disappearing. The mark rides the thread_resolved event,
so the panel's `x`, |:ReviewModeResolveThread|, |:ReviewModeUnresolveThread|
and the GitLab provider all show it, and it uses its own namespace so it never
disturbs the comment signs or virtual text. comments.resolve_flash_ms is how
long it lasts in milliseconds; 0 turns it off.

                                                       *review-mode-reactions*
The panel's `+` key and |:ReviewModeReact| toggle one of GitHub's eight
reactions on a comment. Your own reactions are highlighted with
ReviewModeReactionOwn and marked in the picker, and choosing one you already
added removes it. Nothing is confirmed first: a reaction is cheap to undo.
Comments loaded through the REST fallback can only gain a reaction; removing
one needs a GraphQL id they do not carry, so removal is refused.

                                                           *review-mode-draft*
|:ReviewModeReply|, |:ReviewModeCompose| and the panel's `r` and `R` keys open a
markdown draft buffer rather than a vim.ui.input prompt, so a reply can be more
than one line and can be edited before it goes out. Nothing reaches GitHub
until the draft is confirmed.

        <C-s>   post, after a prompt showing what will be sent
        :w      same as <C-s>
        <C-r>   quote the lines selected in the code window, with their path
                and line numbers
        <C-g>   seed a ```suggestion block from the lines the draft targets
        <C-p>   queue the comment in the pending review instead of posting it
                (new comments only) |review-mode-pending|
        q       discard the draft

<C-r> is what lets a reply point at lines other than the one the thread is
anchored to: select them in the code window, return to the draft, press it.

==============================================================================
PENDING REVIEW                                             *review-mode-pending*

Comments can be batched into one review instead of posting one at a time. <C-p>
in the draft buffer queues the comment; |:ReviewModePending| opens the review
buffer with every queued comment, and the review body is whatever is typed
below the marker line.

        <CR>    jump to the draft's line
        dd      drop the draft under the cursor
        <C-s>   submit as a COMMENT review
        <C-a>   submit as an APPROVE review
        <C-x>   submit as a REQUEST_CHANGES review
        q       close the buffer

Every submission is confirmed first, showing the event and the number of
comments. |:ReviewModeSubmit| does the same without the buffer.

Queued comments render as pending threads in the panel and in
|:ReviewModeThread|, persist in stdpath("state")/review-mode-reviews across
restarts, and are cleared only once GitHub accepts the review; a failed
submission keeps them. GitHub requires a review body for REQUEST_CHANGES, and
for a COMMENT review carrying no comments.

Replies are never batched: the reviews endpoint only accepts new comments, so
|:ReviewModeReply| still posts immediately. A pending review started in the
GitHub web UI is not merged with these drafts.

                                                        *:ReviewModeSummary*
:ReviewModeSummary
        Show file, comment, thread, and viewed-sync counts.

                                                        *:ReviewModeCheckout*
:ReviewModeCheckout {number|url}
        Review a PR without checking it out. Fetches the PR head into
        refs/review-mode/pr/{number} (pull/{number}/head, so fork PRs work),
        puts a detached worktree for it under
        stdpath("cache")/review-mode/worktrees/{owner}_{repo}/pr-{number}, and
        opens the review in its own tabpage with a tab-local cwd. The current
        checkout, branch and working tree are untouched. Set the
        hooks.prepare_checkout override to create the worktree with your own
        tool and return its path instead.

                                                        *:ReviewModeCheckoutClean*
:ReviewModeCheckoutClean [pr]
        Remove review worktrees created by |:ReviewModeCheckout|, after a
        confirmation. Worktrees with uncommitted changes, and the one the
        current session is using, are refused and listed. A dirty worktree is
        also never updated: reviewing its PR again reuses it as it stands and
        warns.

                                                        *:ReviewModeQuickfix*
:ReviewModeQuickfix [unresolved|all]
        Fill the quickfix list with the PR review threads and open it. The
        default follows comments.show_resolved; "all" also lists resolved
        threads, marked [resolved].

:ReviewModeDiagnosticsToggle
        Toggle review threads as vim.diagnostic entries.

                                                        *:ReviewModeSuggestionPreview*
:ReviewModeSuggestionPreview [inline|split]
        Toggle a preview of the suggestion on the current line without
        applying it. "inline" (the default) draws the suggested lines as
        virtual lines under the lines they replace; "split" shows the file
        with the suggestion applied side by side against the file as it
        stands. See |review-mode-suggestions|.

                                                        *:ReviewModeSuggestionAcceptAll*
:ReviewModeSuggestionAcceptAll
        Apply every suggestion in the current file as a trial, after a
        confirmation saying how many and in which file. Applied bottom-up, so
        an earlier application cannot move the lines a later one is anchored
        to.

                                                        *:ReviewModeSuggestionRevert*
:ReviewModeSuggestionRevert [id]
        Put back the lines a trial suggestion replaced: the trial under the
        cursor, or the one with this id from |:ReviewModeSuggestionList|.

                                                        *:ReviewModeSuggestionList*
:ReviewModeSuggestionList
        List the trial suggestions that are applied but not saved, with the
        file and line each one now sits on.

PICKER PROVIDERS                                          *review-mode-pickers*

ReviewMode can use vim.ui.select, snacks.nvim, or Telescope for
:ReviewModeActions and :ReviewModeViewedList. The default picker.provider =
"auto" tries snacks.nvim first, then Telescope, then vim.ui.select. Set
picker.provider to "native", "snacks", or "telescope" to prefer one provider.

The "native" provider is plain vim.ui.select: same file labels, but no diff
preview, no live filtering and no in-picker viewed toggle. External providers
are optional. If a requested provider is unavailable or fails, ReviewMode falls
back to vim.ui.select.

FEWER GITHUB API CALLS                                  *review-mode-api-calls*

comments.conditional_requests (default true) revalidates the REST comment list
with If-None-Match once comments.cache_ttl_seconds is up, instead of
re-downloading it. GitHub answers an unchanged page with 304 Not Modified,
which costs nothing against the rate limit, and the cached comments are served
with their timestamp refreshed. GitHub's ETags are per page, not per
collection, so one ETag and one payload are stored per page and each page is
revalidated on its own. The GraphQL review-thread query is the primary comment
path and is a POST, which GitHub does not answer with 304; it still goes by
comments.cache_ttl_seconds.

performance.gh_metadata_cache (default "10m") is the duration passed to
`gh api --cache` for reads that repeat and cannot go stale in a way that
misleads - today the PR's GraphQL node id, which never changes. The PR head
SHA, :ReviewModeStatus and :ReviewModeChecks are deliberately left uncached.
`--cache` is a flag of `gh api` alone; `gh pr view` and `gh repo view` reject
it.

:ReviewModeSummary and review_mode.api.request_stats() report how many gh
invocations the session spent and how many were answered 304.

ReviewMode loads PR metadata and changed-file status asynchronously. If
GH_REVIEW_BASE is set by a launcher, changed-file loading starts immediately
without waiting for GitHub metadata. Hunk locations are loaded lazily per file,
with immediate focused-file prefetch, opportunistic gitsigns.nvim hunk-cache
reuse, and an optional delayed background scan for PRs under
performance.background_hunk_scan.max_files.

The nvim-tree integration marks unviewed changed files and closed parent
folders with `☐ N`, where `N` is the number of unviewed changed files under
that node. Viewed files and closed folders use `✓`, and files and closed
folders with unresolved comments also use ` N`. An open folder hides these
folder markers because its children show the same state inline. A folder
switches to viewed after every changed file under it is viewed.

External launchers can provide GH_REVIEW_REPO, GH_REVIEW_PR, GH_REVIEW_BASE,
and GH_REVIEW_HEAD to avoid startup discovery calls, or GL_REVIEW_MR,
GL_REVIEW_REPO, GL_REVIEW_BASE and GL_REVIEW_HEAD for GitLab.

:ReviewModeCheckout reviews a PR in a detached worktree of its own instead,
leaving the current checkout alone; review worktrees are only ever removed by
:ReviewModeCheckoutClean, which is what checkout.cleanup = "manual" means. The
hooks.prepare_checkout override decides where that worktree comes from, and
the checkout_ready and checkout_removed events report when one is ready or
gone.

Viewed state is persisted in stdpath("state")/review-mode-state.json by default.
Set viewed.sync = true or run :ReviewModeViewedSyncToggle to pull GitHub's PR file
viewed state at startup and push local viewed/unviewed toggles back to GitHub.

ReviewModeOldToggle uses the built-in Neovim side-by-side diff backend by
default. Set diff.layout = "unified" or run :ReviewModeDiffLayoutToggle to use an
inline unified diff buffer in the current window instead. Closing unified mode
restores the original file buffer. Both layouts hold the whole file and fold
the unchanged regions, so zR shows everything, zM condenses again and zo / zc
open or close one gap. Unified diffs keep diff.unified_context lines visible
around each change; diff.full_file = true opens diffs with every fold open. When diff.use_fast_diffopt is
enabled, side-by-side diffs temporarily apply diff.fast_diffopt and restore the
previous diffopt when the split closes. Unified diffs highlight changed spans
inside modified lines with DiffText; set diff.partial_line_highlights = false
to disable those inline spans.

                                                    *review-mode-diagnostics*
Set comments.diagnostics.enabled = true (or run :ReviewModeDiagnosticsToggle)
to publish every visible thread as a vim.diagnostic entry in the
review_mode_diagnostics namespace, so ]d, vim.diagnostic.open_float, Trouble
and statusline diagnostic counts work on review comments. The message is the
latest comment's author and first line, with a reply count, and user_data
carries the thread id and comment URL. Unresolved threads default to INFO,
resolved and outdated ones to HINT; comments.show_resolved decides whether
resolved threads appear at all.

It is off by default because it mixes review comments into every diagnostic
consumer. The namespace itself draws nothing (comments.diagnostics.display sets
signs, virtual_text and underline to false), because the plugin already draws
comment signs and end-of-line virtual text and the two displays would double up.

:ReviewModeQuickfix fills the quickfix list with the same threads across every
changed file, and review_mode.api.quickfix_items() returns those items without
setting the list.

==============================================================================
GITLAB                                                      *review-mode-gitlab*

GitLab merge requests are reviewed the same way pull requests are. The provider
comes from the origin remote: any host containing "gitlab", or listed in
gitlab_hosts, uses `glab` instead of `gh`. Set provider = "github" or "gitlab"
to decide it yourself, and authenticate glab for the project.

A launcher can hand the session over with GL_REVIEW_MR, optionally with
GL_REVIEW_REPO, GL_REVIEW_BASE and GL_REVIEW_HEAD, mirroring GH_REVIEW_*.
Setting GL_REVIEW_MR also selects the GitLab provider.

Supported: MR metadata, diff discussions loaded as threads, starting a thread on
a line or range, replying, and resolving. A thread id is a GitLab discussion id,
so |review_mode.api| reply and resolve take that instead of a review thread id.
A range comment anchors to its last line.

GitHub-only for now, and reported as "not supported on GitLab yet" instead of
calling gh: viewed-state sync (local viewed state still works), reactions,
comment edit and delete, pending comments and review submission,
:ReviewModeCheckout, :ReviewModeStatus and :ReviewModeChecks. Review diagnostics
and :ReviewModeQuickfix are forge-independent and work on GitLab too. :ReviewModeSuggest posts GitHub suggestion syntax, which
GitLab does not read the same way.

==============================================================================
LOCAL REVIEWS                                                *review-mode-local*

:ReviewModeLocal [<base>] [<head>] reviews two refs in this checkout, with no
PR, no remote and no network. <base> defaults to the merge base with the repo's
default branch; <head> defaults to the working tree, so uncommitted edits are
part of the review. One argument may be a range ("main..feature"). The base is
always resolved to the merge base with the head, so a local review compares what
a PR would.

provider = "local" selects it explicitly, and a repo with no origin remote
selects it on its own. The changed-file list, hunk navigation, the diff views,
viewed state, the panel, diagnostics and the quickfix list are unchanged.
:ReviewModeChecks, :ReviewModeStatus, :ReviewModeBrowser and :ReviewModeCopyUrl
report that they are not supported in a local review instead of calling gh.

Comments are kept on disk, at:

    <git-dir>/review-mode/<branch-or-head>.json

<git-dir> is `git rev-parse --git-dir`: .git in a normal checkout and
.git/worktrees/<name> in a linked worktree, so parallel worktrees never share
review comments. It is not --git-common-dir, which is shared, and git never
tracks any of it. The file is indented with a stable key order so a human or an
agent can read it. Comments load into the same normalized shape GitHub and
GitLab comments do.

:ReviewModeLocalComments opens a review-mode://local buffer with every local
comment grouped by file: <CR> jumps, r replies, R resolves, e edits, dd deletes.

For agents, the whole loop works headless through |review_mode.api|:

    api.review_local(args)                    start the session
    api.local_comment(opts, cb)               create a thread; cb(true, thread)
    api.threads(opts)                         read them back
    api.reply / api.resolve                   add to, or resolve, a thread
    api.edit_comment / api.delete_comment     change or remove a comment
    api.local_store()                         the JSON file's path

For example: >
    nvim --headless -u NONE -c 'lua require("review_mode").setup()' \
      -c 'lua require("review_mode.api").review_local({ "main" })' \
      -c 'lua require("review_mode.api").local_comment({
            path = "init.lua", line = 10, body = "why?", author = "agent" })' \
      -c qa
<
local_comment's author defaults to git config user.name and falls back to
"agent"; it is never a GitHub login.

SUGGESTIONS                                            *review-mode-suggestions*

A `suggestion` block in a review comment is a concrete replacement for the
lines it hangs off. Four ways to deal with one, over the same core. None of it
is GitHub-specific: a local review's threads (|review-mode-local|) carry
suggestion blocks like any other, and the same keys work on them.

In the code: the panel's `p` key and |:ReviewModeSuggestionPreview| draw the
suggested lines as virtual lines under the lines they would replace, in the
panel's diff colours, with the replaced range painted as a deletion. Nothing is
written and no window opens.

Side by side: |:ReviewModeSuggestionPreview| split shows the file with the
suggestion applied against the file as it stands, in the same side-by-side diff
|:ReviewModeOldToggle| uses, folds and partial-line highlights included. It
replaces an open base diff, and toggling it again closes it.

Trial apply: the panel's `a` key and |:ReviewModeApplySuggestion| write the
suggestion into the buffer and leave it there, unsaved, with a "T" sign and a
"trial suggestion" label over the changed range. Run the code, see how it
behaves, then |:ReviewModeSuggestionRevert| to put the original lines back.
Several trials can be live at once; |:ReviewModeSuggestionList| shows them.

Reverting does not rely on `u`. The applied range is tracked with an extmark,
so it restores exactly the lines the suggestion replaced, wherever they have
moved to since, and leaves edits elsewhere in the file alone.

Accept all: the panel's `A` key and |:ReviewModeSuggestionAcceptAll| apply every
suggestion in the file after a confirmation. Bottom-up, because a suggestion can
replace one line with three, and applying the top one first would move every
line number below it.

Trials are buffer state, not review state, and the plugin does not track git:

- Save or commit while a trial is live and it becomes an ordinary edit. Nothing
  is unwound, and reverting afterwards only changes the buffer again; it does
  not touch what was written to disk or committed.
- Reloading the buffer (:e!, or an autoread re-read) drops its trials and
  previews. Whatever the file holds then is what you have.
- Stopping the session forgets every trial for the same reason, and does not
  undo them.

The hooks on_suggestion_accepted and on_suggestion_reverted, and the API calls
behind all of this, are in |review-mode-setup| and the README.
